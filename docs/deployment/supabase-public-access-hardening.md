# Sécurisation des référentiels et des imports Supabase

La migration `20261104095537_public_catalogue_and_import_rpc_security.sql` ferme deux accès anonymes constatés sur l’API : les trois référentiels DPR sans RLS et les trois anciennes RPC de rapprochement SharePoint exécutées avec les privilèges de leur propriétaire.

Les référentiels globaux `emergency_exercise_types`, `port_call_reason_types` et `waste_types` restent lisibles par les utilisateurs connectés. Administrateur, Direction et Armement conservent leur maintenance dans leur entreprise active. Le rôle technique `service_role` conserve les lectures et écritures nécessaires aux imports DPR. Les droits anonymes et les droits interactifs de troncature sont retirés. Les politiques RLS sont créées dans la même migration pour préserver les listes utilisées par DPR et les indicateurs QHSE.

Les RPC `resolve_sharepoint_document_links`, `resolve_sharepoint_hr_document_links` et `resolve_sharepoint_planning_links` deviennent `SECURITY INVOKER`. Leur exécution est réservée à l’import technique par `service_role` et au SQL lié exécuté par `postgres`. Une garde dans chaque fonction refuse également les profils interactifs, même si un droit d’exécution était ajouté ultérieurement par erreur. Les signatures et les résultats des RPC restent inchangés.

Ces fonctions sont appelées par les outils CLI SharePoint ; aucun écran applicatif ne les appelle directement. Les imports API doivent employer `SUPABASE_SERVICE_ROLE_KEY`, conservée exclusivement dans leur environnement privé. Le repli historique sur une clé anonyme ne constitue plus un chemin d’import autorisé. Le parcours d’import SQL lié reste disponible. Certaines bibliothèques anciennes ne possèdent pas de colonne d’entreprise : ces rapprochements globaux restent une opération technique, sans prétendre fournir une isolation par entreprise à un utilisateur interactif.

La migration ne change ni les données existantes, ni les règles RH, ni les buckets de documents, ni le chargement public du logo. Elle ne modifie aucun paramètre de réseau ou d’obligation TLS de la base. Les clients SeaPilot utilisent l’API HTTPS ; les connexions PostgreSQL directes et les imports SQL liés doivent être contrôlés séparément avant de restreindre les adresses IP ou d’exiger TLS.

La recette SQL `supabase/tests/public_catalogue_and_import_rpc_security_test.sql` utilise cinq comptes synthétiques et des entrées fictives, dans une transaction annulée. Elle vérifie la lecture des listes pour les cinq profils, la maintenance par les rôles de bureau, le refus des écritures Capitaine/Marin, la conservation de l’accès technique et le refus des RPC par les utilisateurs interactifs et anonymes. Les RPC de rapprochement ne sont jamais exécutées sous un rôle autorisé pendant cette recette afin de ne pas rapprocher de véritables données importées.

La migration a été appliquée le 4 novembre 2026. La recette SQL a réussi ; les 58 tests des imports SharePoint et les 17 tests des requêtes et migrations DPR ont également réussi. Les contrôles HTTP avec une clé publique active et sans session renvoient désormais `401` pour les trois catalogues et les trois RPC. Les droits techniques de lecture et de mise à jour des tables importées restent présents. Le contrôle de sécurité ne signale plus les trois tables publiques sans RLS. Aucune donnée existante n’a été modifiée par la migration ; les comptes et entrées de recette ont été annulés.
